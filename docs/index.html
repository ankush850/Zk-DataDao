Overview & Introduction

What ZK-DataDAO is, the problem it solves, and key concepts

ZK-DataDAO

Buy or sell data without compromising your privacy — powered by Zero-Knowledge Proofs on the Filecoin Virtual Machine.

🔐 ZK-SNARKs ⚙️ Filecoin FVM 📦 IPFS Storage 🏛️ DAO Governance 🗃️ Tableland SQL

What is ZK-DataDAO?

ZK-DataDAO is a decentralized, privacy-preserving data marketplace built on the Filecoin Virtual Machine (FVM). It enables the creation and management of DAOs (Decentralized Autonomous Organizations) specifically designed for collecting, contributing, and monetizing datasets.

The platform uses Zero-Knowledge Proofs (ZKP) to allow contributors to prove they meet eligibility criteria set by DAO operators — such as being a member of a specific Discord server — without ever revealing their identity or private data.

The Problem It Solves

🔒

Privacy in Data Markets

Traditional data markets require contributors to expose their identity. ZK-DataDAO uses cryptographic proofs so identity stays private.

🤝

Trustless Eligibility

DAO operators set joining conditions without trusting a centralized server to verify them. The proof IS the verification.

💾

Decentralized Storage

Data is stored on Filecoin — not a centralized cloud — ensuring permanence and censorship resistance.

💰

Automated Rewards

Reward pools locked in smart contracts are automatically distributed to valid contributors with no middleman.

Three-Actor Model

ActorRoleKey Actions
🏭 DAO OperatorCreates and manages the DAOSet eligibility rules, fund reward pool, define data format, release funds
👤 Data ContributorProves eligibility and submits dataGenerate ZK proof, join DAO, upload data to IPFS/Filecoin, earn FIL rewards
🌐 Filecoin NetworkTrustless infrastructure layerStore data permanently, process transactions, run smart contracts
✅ The ZK Barrier
The defining feature is the Zero-Knowledge Barrier: contributors prove they satisfy joining conditions without revealing any private information. A contributor can prove "I am a member of Discord server X" without the smart contract learning their Discord username, email, or any personal data. Only a cryptographic proof goes on-chain.

Smart Contracts

Detailed breakdown of all three Solidity contracts

Contract 1: DAO.sol

The core DAO contract. Each DAO is an independently deployed instance of this contract. Operators deploy new instances via the frontend; the contract holds the reward pool and tracks members.

Soliditycontracts/DAO.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract DAO {
    address[] public members;       // all joined contributors
    address public owner;           // DAO creator / operator
    uint256 public rewardAmount;    // total reward pool (wei)
    uint capacity;                  // max number of members

    // Deploys DAO and locks reward funds in the contract
    constructor(uint256 _rewardAmount, uint _capacity) payable {
        require(msg.value == _rewardAmount);
        owner = msg.sender;
        rewardAmount = _rewardAmount;
        capacity = _capacity;
    }

    // Called after ZKP verification passes
    function joinDAO() external {
        require(members.length < capacity, "DAO is full");
        members.push(msg.sender);
    }

    // Operator distributes reward equally among eligible members
    function sendReward(address payable[] memory eligibleMembers) external payable {
        require(msg.sender == owner, "Only owner can disburse rewards");
        uint amount = rewardAmount / eligibleMembers.length;
        for (uint i = 0; i < eligibleMembers.length; i++) {
            eligibleMembers[i].transfer(amount);
        }
    }
}

Zero-Knowledge Proof System

How ZK proofs are defined, generated, and verified

What is a ZK-SNARK?

A Zero-Knowledge Succinct Non-Interactive Argument of Knowledge allows one party (the prover) to convince another (the verifier) that they know a secret value satisfying some constraint — without revealing the secret itself. ZK-DataDAO uses this to prove "I qualify for this DAO" without revealing personal data.

The Circom Circuit

CircomZKP/server_verify.circom
pragma circom 2.0.0;

template server_verify() {
   // Private input: user's actual eligibility value
   signal input in;

   // Public output: committed result
   signal output req;

   // Constraint: pass the input through
   req <== in;
}
component main = server_verify();

ZoKrates Circuit (used in-browser for Discord)

ZoKrates DSLInline in ZKdiscord.jsx
// Proves: private value 'a' equals public requirement 'b'
def main(private field a, field b) {
    assert(a == b);
    return;
}
// a = 1 (IS in Discord server) or 0 (NOT in server)  [PRIVATE]
// b = 1 (requirement: must be a server member)         [PUBLIC]
// Proof only passes if user is actually in the server

Proof Generation Flow (In Browser)

1
Discord OAuth

User authorizes app → Discord returns access token with guilds scope

2
Membership Check

App calls GET /api/users/@me/guilds. Checks if required server name is in list. Sets user = 1 or 0

3
Circuit Compilation

ZoKrates compiles the DSL source to arithmetic constraints in browser memory

4
Witness Computation

Assigns values to all circuit signals satisfying constraints

5
Proof Generation

Creates Groth16 proof: three elliptic curve points (A, B, C)

6
Local Verification ✅

Pairing check confirms proof. If user is NOT in server, proof generation throws — they cannot fake membership.

Trusted Setup Ceremony Files

⚠️ Trusted Setup Security
The security assumption is that at least ONE participant in the MPC ceremony destroys their randomness ("toxic waste"). If all collude and keep their secrets, they could forge proofs. Multi-party ceremonies with diverse participants are preferred for production.

Tableland Overview

Tableland is a decentralized, SQL-compatible database protocol. Data is stored as EVM transaction events, making it permissionless and queryable. ZK-DataDAO uses two Tableland tables deployed on Filecoin Hyperspace.

Glossary

Key terms and concepts used throughout this documentation

TermDefinition
ZK-SNARKZero-Knowledge Succinct Non-Interactive Argument of Knowledge. Proves knowledge of information without revealing it.
Groth16A ZK-SNARK proving system with constant-size proofs and fast on-chain verification. Used by ZK-DataDAO.
CircomA domain-specific language for defining arithmetic circuits that represent ZK constraints.
ZoKratesA high-level ZKP toolbox with its own DSL. Used in-browser for the Discord membership proof.
WitnessAn assignment of values to all circuit signals — the complete solution to the constraint system.
Trusted SetupA one-time ceremony generating proving and verification keys. Security depends on participants destroying their randomness.
Powers of TauA universal trusted setup ceremony reusable across circuits. The pot14_final.ptau supports up to 16,384 constraints.
DAODecentralized Autonomous Organization. Here, each DAO is a separately deployed autonomous contract instance.
Filecoin FVMFilecoin Virtual Machine — an EVM-compatible execution environment on the Filecoin network.
TablelandA decentralized SQL database protocol built on EVM chains. Data stored as transaction events.
CIDContent Identifier. A cryptographic hash used by IPFS to uniquely identify content.
CAR fileContent Addressable aRchive. A format for packaging IPFS data for Filecoin storage deals.
Piece CID / commPA Filecoin-specific identifier computed from a CAR file, used to uniquely identify a storage deal.
Market Actor (f05)Filecoin's built-in actor managing storage deals. DealClient.sol interacts with it via system precompiles.
CBORConcise Binary Object Representation. Filecoin's serialization format for actor messages and deal proposals.
FRC42Filecoin Request for Comment 42. Standard method dispatch protocol for EVM actors receiving Filecoin actor messages.
bn128A BN elliptic curve (also BN254/alt_bn128) used for efficient Groth16 pairing operations.
wagmiReact hooks library for EVM wallet connection, contract reads/writes, and transaction management.
viemTypeScript interface for Ethereum. Used for low-level contract deployment in ZK-DataDAO.
